# Driver API contract

From spike 011 (`specs/011-driver-api-contract/`), where every decision is in the Log. This is the provider-neutral boundary that every driver kit is written against. The engine's HTTP driver API is the contract. The MCP gateway mirrors part of it as MCP tools and forwards the caller's driver token unchanged (spec 010 Q20). The components and flows around it are in `docs/architecture/`. A worked run is in `happy-path.md`.

Schemas are drafts. They name fields and types, not final JSON Schema. Spike 9 picks the libraries, and milestone 1 turns these into JSON Schema files with tests.

## Principles

- **Neutral.** No Claude Code or SDLC terms in requests or responses. The kit maps the engine's answers to its hook output (for example `permissionDecision`), and the definition supplies the workflow's words (spec 010 Q3; Art. 3). The spike 005 stub, which returned Claude Code hook JSON from the engine, is not carried over.
- **Pull only.** The engine never calls a driver. Everything a driver needs to choose its next action is in `status` (Art. 9).
- **One contract version.** Every path starts with `/v1`. The kit declares the `contract_version` it was built for when it registers a session.
- **Idempotent mutations.** Every mutating call carries an `Idempotency-Key` header with IETF draft-07 semantics: a retry returns the stored result, and the same key with a different payload is refused (spec 010 Q16).
- **Useful denials.** Every refusal says what was refused, why, and what to do next.

## Authentication

- Every call carries `Authorization: Bearer <driver token>`. There is one static token per user, stored hashed; the same token works for hooks, the MCP gateway, and OTLP (spec 010 Q4, Q14). A missing or wrong token gets `401`.
- Driver tokens never carry approval or publish scopes (Art. 2). They may operate the user's own leased runs, read definitions and analysis, and submit drafts (spec 010 Q15).
- MCP calls carry no Claude Code session ID. Tools that need the calling session take a `session_id` argument, which the kit's PreToolUse hook fills in with `updatedInput`; the agent never supplies it (Q3, to confirm by trial).

## Operations

| Operation | HTTP | MCP tool | MVP | Caller |
| --- | --- | --- | --- | --- |
| Register session | `POST /v1/sessions` | — | build | SessionStart hook; PreToolUse for an unknown session |
| Gate (authorize action) | `POST /v1/sessions/{session_id}/gate` | — | build | PreToolUse hook, every tool call |
| Record activity | `POST /v1/sessions/{session_id}/activity` | — | build | PostToolUse hook, async |
| Report iteration | `POST /v1/sessions/{session_id}/iterations` | — | build | Stop hook |
| Status | `GET /v1/status?session_id=…` or `GET /v1/runs/{run_id}/status` | `status` | build | agent; SessionStart (through register) |
| Start run | `POST /v1/runs` | `start_run` | build | agent |
| Request transition | `POST /v1/runs/{run_id}/transition-requests` | `request_transition` | build | agent |
| Get definition | `GET /v1/workflows/{workflow}/versions/{version\|current}` | `get_definition` | build | agent (feedback loop) |
| Submit draft | `POST /v1/workflows/{workflow}/drafts` | `submit_draft` | build | agent (feedback loop) |
| Get analysis | analysis API (spec 010 Q23) | `get_analysis` | build | agent (feedback loop) |
| Submit evidence | `POST /v1/runs/{run_id}/evidence` | `submit_evidence` | specified only | agent |
| Get evaluation task | `GET /v1/evaluation-tasks/{task_id}` | `get_evaluation_task` | specified only | driver-side evaluator |
| Submit step result | `POST /v1/evaluation-tasks/{task_id}/result` | `submit_step_result` | specified only | driver-side evaluator |

Folded in (Q8): `checkpoint_status` and `allowed_actions` are parts of `status` (`open_attempt`, `permitted_transitions`, `protected_actions`). `bind_session` happens in register (an existing run on the session's subject) and in `start_run` (a new run).

The engine's introspection endpoint, its paged event read, and the analysis API are also part of the engine's HTTP surface, but they belong to the analysis service, not to drivers (spec 010 Q23).

## Hook endpoints

### Register session

`POST /v1/sessions`. Idempotency key: generated by the hook script per call.

```yaml
request:
  session_id: string            # the agent's own session ID
  source: string                # why the session started: startup | resume | clear | fork | lazy
  run_inputs: { <name>: string } # what the kit can compute locally, e.g. repository and branch from cwd
  driver:
    provider: string            # e.g. "claude-code"; recorded, never interpreted
    agent_version: string
    model: string
    kit_version: string
    contract_version: string    # "v1"
    capabilities: [core | activity_recording | evaluation | enforcement | telemetry]
response:
  session: { id, user, bound_run_id: string | null }
  summary: string               # compact status for SessionStart, see "Status"
```

If the session's `run_inputs` match an active run of a workflow the user may operate, the engine binds the session to it. A bind checks the lease (another user's run is refused) and the run's `required_capabilities`. A session that is refused stays registered and unbound, and `summary` says why.

### Gate

`POST /v1/sessions/{session_id}/gate`. Idempotency key: the agent's tool use ID.

```yaml
request:
  tool_use_id: string
  action:                       # present only when the kit maps the tool call to a protected action
    name: string                # e.g. "merge"
    revision: string
response:                       # always 200, so a hook script's error handling cannot swallow the reason
  decision: allow | deny
  denial: Denial | null         # see "Denials"
```

- With no `action`, the gate is a liveness check and the trigger for lazy registration: an unknown `session_id` gets `deny` with code `session_unknown`, and the script registers and retries once.
- With an `action`, the engine checks that the current stage is in the action's `allowed_in`, that `revision` equals the revision the last passing checkpoint reviewed, and that the session's user holds the lease (spec 010 Q3).
- An engine outage blocks the tool call: the hook runs with `onFailure: "block"` (spec 005 Q6).

### Record activity

`POST /v1/sessions/{session_id}/activity`. Idempotency key: the tool use ID. Response: `202`.

```yaml
request:
  tool_use_id: string
  tool: string                  # the agent's tool name, recorded as-is
  input: object                 # redacted by the kit
  outcome: success | error
  duration_ms: integer
  agent: { id: string | null, type: string | null }  # subagent, when the agent has one
```

### Report iteration

`POST /v1/sessions/{session_id}/iterations`. Idempotency key: generated by the hook script per call.

```yaml
request:
  self_check:                   # the agent's own check against the stage task's acceptance criteria
    criteria_met: boolean
    unmet: [string]             # the criteria not met, by their text
  last_message: string | null   # trimmed
response:
  verdict: continue | stop
  reason: string                # shown to the agent on continue
  used: { iterations, wall_time, consecutive_failed_checks }
  limits: { iterations, wall_time, failed_checks }
```

- The engine counts iterations and measures wall time itself, and returns the verdict (Q4). The kit holds no limit logic.
- A self-check with `criteria_met: false` counts as one failed check (Q5).
- When a limit is reached before the criteria are met, the stage task is exhausted: the engine opens an escalation for the owner, and the verdict is `stop` with the reason (sequence 6).
- A session with no bound run, or a run waiting on a human, gets `stop`.

## MCP tools

Each tool is a thin mirror of the HTTP call above it. The gateway:

- forwards the caller's token unchanged;
- sets `Idempotency-Key` to a hash of the user, the tool name, and the canonical arguments (Q2);
- returns the engine's response as `structuredContent`, plus the same JSON as a text block;
- turns a denial into a result with `isError: true` whose text is the denial's `message` and `recovery`, so the agent reads them (MCP tools, 2026-07-28).

Mutating tools carry a precondition echoed from `status`, so that a deliberate retry is a different payload with a different key, while a blind retry of a lost response returns the stored result (Q2).

### `status`

```yaml
input:
  session_id: string            # injected by the hook
  run_id: string | null         # defaults to the session's bound run
output: Status                  # see "Status"
```

### `start_run`

```yaml
input:
  session_id: string            # injected by the hook
  workflow: string              # from status.startable_workflows
  run_inputs: { <name>: string }
output: Status | Denial         # subject_busy, missing_capability, session_unknown, invalid_inputs, not_permitted
```

The engine derives the subject key from the inputs the definition marks (Q1), refuses the call if an active run already has that key, creates the run on the current published version, binds the session, and acquires the lease for the user.

### `request_transition`

```yaml
input:
  session_id: string            # injected by the hook
  run_id: string
  transition: string            # from status.permitted_transitions
  revision: string              # the pushed revision the checkpoint reviews
  expected_attempts: integer    # echoed from status.permitted_transitions[].attempts
output:
  result: committed | attempt_open | denied
  attempt_id: string | null
  denial: Denial | null
  status: Status
```

- With no checkpoint on the edge, the engine commits the transition at once (`committed`).
- With a checkpoint, it opens an attempt (one per run) and returns `attempt_open`. The checkpoint then progresses without the driver (sequence 3). The driver learns the outcome by calling `status`.

### `get_definition`, `submit_draft`, `get_analysis`

```yaml
get_definition:
  input: { workflow: string, version: integer | "current" }
  output: { workflow, version, state: published | superseded | draft, yaml: string }
submit_draft:
  input: { workflow: string, base_version: integer, yaml: string, hypothesis: string }
  output: { draft_id: string } | Denial   # validation_failed carries each schema or semantic rule error
get_analysis:
  input: { workflow: string, version: integer | "current" }
  output: analysis summary (weakest step, pass and rework rates, evaluator agreement); shape owned by the analysis service
```

A driver may submit drafts but never publish them; a human approves in the UI (Art. 2).

### Specified only

```yaml
submit_evidence:                # for workflows whose content does not live in git
  input: { session_id, run_id, type: string, payload: object, revision: string }
  output: { evidence_id } | Denial
get_evaluation_task:            # a driver-side evaluator fetches the packet by ID only (spec 005)
  input: { task_id: string }
  output: EvaluationTask
submit_step_result:
  input: { task_id: string, result: { raw_score: number, rationale: string } }
  output: { accepted: boolean } | Denial
```

## Status

`status` carries everything a generic driver needs to choose its next action, and nothing workflow-specific beyond what the definition says (Art. 9).

```yaml
Status:
  contract_version: "v1"
  session: { id, bound_run_id }
  startable_workflows:          # only when the session has no bound run (Q7)
    - { workflow, version, title, description,
        run_inputs: [{ name, description, required, part_of_subject_key }] }
  run:                          # null when unbound
    id: string
    workflow: string
    version: integer
    state: active | completed | failed | excluded
    subject_key: string
    run_inputs: { <name>: string }
    owner: string
    lease_holder: string
  stage:
    id: string
    visit: integer
    entered_at: timestamp
    task:
      prompt: string            # rendered
      acceptance_criteria: [string]   # rendered
      limits: { iterations, wall_time, failed_checks }
      used: { iterations, wall_time, consecutive_failed_checks }
      state: working | exhausted
  permitted_transitions:
    - id: string
      to: string
      rework: boolean
      attempts: integer         # attempts so far on this transition; echo as expected_attempts
      checkpoint:               # null when the edge has none
        label: string
        steps:
          - { id, executor, role, runs_in, points,
              rubric: [{ id, range, descriptor }] | null,   # rendered (Q10)
              min_score: number | null, scale: [number, number] | null,
              council: integer | null }
  protected_actions:
    - { name, allowed_now: boolean, reviewed_revision: string | null }
  open_attempt:                 # null when none
    id: string
    transition: string
    revision: string
    steps: [{ id, state: pending | running | passed | failed | not_evaluated }]
    waiting_on: runner | human | null
  last_decision:                # the most recent attempt outcome, transition, or escalation resolution
    kind: attempt_failed | attempt_not_evaluated | transition_committed | override | escalation_resolved
    at: timestamp
    actor_type: engine | human
    reason: string
    failed_steps:               # (Q6)
      - id: string
        outcome: failed | not_evaluated
        reason: string          # one line
        log_tail: string | null # failed command checks, trimmed to a few KB
        members:                # council steps
          - { band: string, rationale: string }
    rework_path: string | null  # the transition to use for rework, if any
  pending:
    human_steps: [{ attempt_id, step_id, since }]
    escalations: [{ id, reason, since }]
    evaluation_tasks: []        # driver-side evaluation; empty in the MVP
  recommendations: []           # shadow typed decisions influence nothing, so empty in the MVP (spec 010 Q28)
  next:
    action: start_run | do_stage_task | request_transition | wait | none
    hint: string                # generic, rendered from the state above
```

- Raw evaluator scores never reach the driver; bands and rationales do (Q6).
- **Summary.** Register returns `summary`: a plain-text rendering of the stage, the task, the permitted transitions, the open attempt, the last decision's one-line reasons, and `next`. The kit injects it at SessionStart. With the kit instructions, it must stay under Claude Code's 10,000-character context cap, so it leaves out rubrics, log tails, and rationales; the agent calls `status` for those (Q11).

## Denials

```yaml
Denial:
  code: string                  # stable enum, below
  message: string               # one plain sentence, names what was refused and why
  recovery: string              # the generic next step
  details: object | null        # e.g. the expected revision, the missing capabilities
```

Over HTTP, MCP-backed calls return denials as RFC 9457 `application/problem+json` (`type` derived from `code`, plus the fields above) with the status below. The gate always answers `200` with `decision: deny`.

| Code | HTTP | When |
| --- | --- | --- |
| `session_unknown` | 404 | the session is not registered (register, then retry) |
| `run_not_found` | 404 | no such run, or not visible to the user |
| `not_permitted` | 409 | the transition is not permitted from the current stage |
| `attempt_open` | 409 | the run already has an open attempt |
| `stale_precondition` | 409 | `expected_attempts` does not match; call `status` again |
| `subject_busy` | 409 | an active run already has this subject key |
| `lease_held` | 409 | another user holds the run's lease |
| `action_not_allowed_in_stage` | 409 | protected action outside its `allowed_in` stages |
| `revision_not_reviewed` | 409 | protected action on a revision other than the reviewed one |
| `stage_task_exhausted` | 409 | the stage task is waiting on the owner's escalation decision |
| `missing_capability` | 403 | the session lacks a capability the definition requires |
| `forbidden_scope` | 403 | the driver token may not do this (approve, publish) |
| `invalid_inputs` | 422 | missing or unknown `run_inputs`, or a malformed request |
| `validation_failed` | 422 | a draft fails schema or semantic rules; `details` lists each error |
| `idempotency_conflict` | 422 | the same key was used with a different payload |

## Capabilities

- A session declares its capabilities when it registers. The engine trusts and records them on the session (Art. 8).
- When a session binds to a run, through register or `start_run`, the engine checks the definition's `required_capabilities` and refuses with `missing_capability` if one is missing (Q9).
- The engine does not compare declared capabilities with observed behaviour in the MVP (for example `enforcement` declared but no gate calls). That is in `BACKLOG.md` "Next".

## Subject key

- The definition marks which `run_inputs` form the subject key. Proposed: a `key` list in the `subject` block, for example `subject: { key: [repository, branch], … }`.
- The engine derives a canonical key from those inputs (their names and values, in the listed order) and stores it opaquely. It enforces at most one active run per workflow and subject key (Q1).
- The kit only sends `run_inputs`. The Claude Code kit computes `repository` and `branch` locally from the session's working directory.

## Evaluation task packet

The runner's evaluator packet (spec 010 G2) and the post-MVP driver-side packet have the same shape:

```yaml
EvaluationTask:
  task_id: string
  run_id: string
  step: { id: string, instructions: string | null, scale: [number, number],
          rubric: [{ id, range, descriptor }] }       # rendered
  subject:
    repository: string
    base: string
    revision: string
    inputs: { <name>: { file: string } | { diff: string } }  # resolved by the evaluator from its own clone
  output_schema: JSON Schema    # { raw_score: number, rationale: string }
  deadline: timestamp
```

- The packet leaves out `min_score` and points, so the fresh-context evaluator is not anchored. The engine applies the pass condition (Art. 6).
- The evaluator diffs its own clone at `revision` against `base`; the driver submits no diff (spec 010 Q26).
